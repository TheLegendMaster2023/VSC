### 3.7. Практика перебазирования (`git rebase`)

Создана ветка `feature/database` от `main`, добавлен файл `config.txt`:
```bash
git checkout -b feature/database
# Внесены параметры SQLite и PostgreSQL
git add config.txt
git commit -m "feat(db): add database configuration"
```

На ветке `main` параллельно зафиксирован коммит с `MySQL`:
```bash
git checkout main
# config.txt: database: MySQL
git commit -m "fix(db): change default database to MySQL"
```

Выполнен rebase ветки `feature/database` на `main`:
```bash
git checkout feature/database
git rebase main
```

Возникший конфликт в `config.txt` разрешён объединением всех СУБД (`MySQL`, `PostgreSQL`, `SQLite`). После этого выполнено добавление файла и продолжение операции:
```bash
git add config.txt
git rebase --continue
```

История коммитов ветки `feature/database` выстроилась строго линейно поверх вершины ветки `main`.

## 5. ОТВЕТЫ НА КОНТРОЛЬНЫЕ ВОПРОСЫ

### 1. Что такое ветка в Git и как она реализована технически?
**Ответ:**  
В Git ветка (branch) технически представляет собой легковесный 41-байтный текстовый файл, хранящийся в каталоге `.git/refs/heads/<имя_ветки>`, внутри которого записан 40-символьный хэш SHA-1 последнего коммита данной ветки (плюс символ перевода строки). При создании коммита указатель ветки просто сдвигается на новый хэш. Текущая активная ветка определяется ссылкой в служебном файле `.git/HEAD`.

### 2. В чём разница между `git merge` и `git rebase`? Когда что применять?
**Ответ:**  
- `git merge` выполняет слияние ветвей с сохранением истинной хронологии. Если ветки разошлись, создаётся отдельный коммит слияния (merge-commit) с двумя родителями. История ветвления остаётся неизменной.
- `git rebase` «перебазирует» коммиты текущей ветки, отрывая их от точки исходного ответвления и заново воспроизводя поверх вершины целевой ветки. Хэши коммитов перезаписываются, а история становится строго линейной.
- **Применение:** Rebase применяется для локальных feature-веток перед отправкой в общий репозиторий, чтобы очистить историю. Merge применяется при слиянии готовых веток в публичные ветки (`main`, `develop`), где нельзя переписывать публичную историю.

### 3. Что такое конфликт слияния и как он возникает?
**Ответ:**  
Конфликт слияния возникает в том случае, когда в двух объединяемых ветках одни и те же строки одного и того же файла были изменены по-разному относительно их общего предка, либо когда файл был удалён в одной ветке и изменён в другой. В этом случае алгоритм трёхстороннего слияния не может автоматически решить, какой вариант является приоритетным, и требует вмешательства разработчика.

### 4. Как разрешить конфликт вручную? Что означают маркеры `<<<<<<<`, `=======`, `>>>>>>>`?
**Ответ:**  
Разработчик открывает конфликтный файл в редакторе:
- `<<<<<<< HEAD` — начало блока изменений из текущей ветки, на которой выполняется слияние.
- `=======` — разделитель между конфликтующими вариантами.
- `>>>>>>> branch-name` — конец блока изменений, пришедших из сливаемой ветки.  
Разработчик вручную удаляет маркеры, формулирует корректную финальную версию строк, индексирует файл командой `git add <файл>` и фиксирует слияние через `git commit`.

### 5. В чём отличие `git reset` от `git revert`? Когда какой использовать?
**Ответ:**  
- `git reset` перемещает указатель ветки назад во времени, удаляя последующие коммиты из истории ветки. Используется **только на локальных, ещё не отправленных на сервер коммитах**. Имеет режимы `--soft` (сохраняет в индекс), `--mixed` (сохраняет в рабочую директорию) и `--hard` (безвозвратно удаляет).
- `git revert` вычисляет противоположные изменения выбранного коммита и создаёт совершенно новый коммит, отменяющий эти действия. История коммитов не переписывается, поэтому `git revert` безопасен и рекомендован для общих публичных веток.

### 6. Что такое fast-forward merge и чем он отличается от трёхстороннего слияния?
**Ответ:**  
- **Fast-forward** (перемотка вперёд) возможен, если целевая ветка не содержит новых коммитов с момента ответвления текущей ветки. Git не создаёт коммит слияния, а просто перемещает указатель целевой ветки вперёд на последний коммит сливаемой ветки.
- **Трёхстороннее слияние (Three-way merge / ort strategy)** происходит, когда в обеих ветках появились независимые коммиты. Git анализирует три снимка: два коммита на верхушках веток и их ближайшего общего предка (merge base), после чего создаёт специальный merge-коммит с двумя родителями.

### 7. Зачем нужна ветка `release` в Git Flow?
**Ответ:**  
Ветка `release/*` изолирует подготовку к выпуску версии от продолжающейся повседневной разработки новых функций. В ней осуществляются:
- Финальное тестирование и исправление мелких ошибок (багфиксы).
- Обновление версий пакетов, документации, генерация changelog.
- При этом новые фичи продолжают спокойно вливаться в `develop`, не дестабилизируя релиз. После завершения релизная ветка вливается как в `main`, так и обратно в `develop`, и помечается релизным тегом.

### 8. Как отправить все локальные ветки в удалённый репозиторий?
**Ответ:**  
Командой:
```bash
git push --all origin
```
А для одновременной отправки всех аннотированных тегов:
```bash
git push --tags origin
```

### 9. Почему rebase считается опасной операцией на общих ветках?
**Ответ:**  
Потому что rebase уничтожает существующие коммиты и создает новые с иными SHA-1 хэшами. Если эти коммиты уже были отправлены в удалённый репозиторий и скачаны коллегами, то при попытке синхронизации у коллег возникнет расхождение истории, дублирование коммитов и многочисленные искусственные конфликты слияния. «Золотое правило Git»: **никогда не делать rebase на публичных, общих ветках**.
