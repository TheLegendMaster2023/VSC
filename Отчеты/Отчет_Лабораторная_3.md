Студент: Мухамеджанов Эльёр Тимурович, группа ПИН-б-о-24-1(2)

    """Сложение двух чисел."""
    return a + b

def subtract(a: float, b: float) -> float:
    """Вычитание b из a."""
    return a - b

def multiply(a: float, b: float) -> float:
    """Умножение двух чисел."""
    return a * b

def divide(a: float, b: float) -> float:
    """Деление a на b с проверкой деления на ноль."""
    if b == 0:
        raise ValueError("Ошибка: Деление на ноль невозможно!")

    print(f"2 + 3 = {add(2, 3)}")
    print(f"10 - 4 = {subtract(10, 4)}")

## 5. ОТВЕТЫ НА КОНТРОЛЬНЫЕ ВОПРОСЫ

### 1. Что такое форк репозитория и зачем он нужен?
**Ответ:**  
Форк (Fork) — это серверная независимая копия репозитория в пространстве имён другого пользователя или организации на платформе (GitLab/GitHub). Форк позволяет разработчику свободно вносить изменения, создавать ветки и экспериментировать с кодовой базой, даже если у него нет прямого права на запись (write access) в оригинальный репозиторий. На основе форка организуется процесс предложения правок в основной проект через Merge Request / Pull Request.

### 2. В чём разница между `git fetch` и `git pull`?
**Ответ:**  
- `git fetch` скачивает метаданные, новые ветки и коммиты из удалённого репозитория в локальную базу данных объектов Git, но оставляет локальные ветки и файлы в рабочей директории нетронутыми.
- `git pull` является комбинацией двух команд: сначала выполняется `git fetch`, а затем полученные изменения сразу объединяются с текущей локальной веткой через `git merge` (или `git rebase` при ключе `--rebase`).

### 3. Зачем добавлять `upstream` при работе с форком?
**Ответ:**  
По умолчанию клонированный форк знает только о своём удалённом сервере (`origin`). Добавление ссылки на оригинальный репозиторий (`upstream`) необходимо для того, чтобы разработчик мог в любой момент загружать свежие изменения, сделанные другими участниками команды в основном проекте (`git fetch upstream`), разрешать конфликты на своей стороне и поддерживать свой форк в актуальном состоянии.

### 4. Что такое Merge Request (Pull Request) и какова его роль в совместной разработке?
**Ответ:**  
Merge Request (в терминологии GitLab) или Pull Request (в GitHub) — это формализованный запрос разработчика к владельцам и мейнтейнерам исходного проекта с просьбой рассмотреть, протестировать и влить изменения из функциональной ветки в целевую ветку (`main`/`develop`). MR служит центральным интерфейсом для проведения Code Review, обсуждения архитектурных решений, автоматического запуска CI/CD тестов и предотвращения попадания нестабильного кода в продакшн.

### 5. Какие этапы проходит MR от создания до слияния?
**Ответ:**  
1. **Создание:** указание исходной ветки (source) и целевой ветки (target), заполнение описания (summary, checklist, связанные issues).
2. **Автоматическая проверка:** запуск CI/CD пайплайна (линтеры, юнит-тесты, проверка сборки).
3. **Code Review:** проверка кода коллегами и тимлидом, комментарии к конкретным строкам diff.
4. **Доработка:** внесение исправлений автором (push новых коммитов в исходную ветку).
5. **Одобрение (Approval):** получение разрешения от уполномоченных ревьюеров.
6. **Слияние (Merge):** вливание ветки в целевую с закрытием связанных задач.
7. **Удаление ветки:** очистка функциональной ветки после завершения задачи.

### 6. Что такое Code Review и зачем он нужен?
**Ответ:**  
Code Review — процесс систематической взаимной проверки исходного кода другими инженерами команды перед его слиянием в общий репозиторий.  
**Цели Code Review:**
- Выявление логических ошибок, уязвимостей безопасности и граничных случаев до попадания в релиз.
- Обеспечение соблюдения стандартов кодирования и архитектурного стиля команды.
- Обмен знаниями между разработчиками и наставничество младших специалистов.
- Поддержание высокого качества документации и тестов.

### 7. Как обновить форк, если исходный репозиторий изменился?
**Ответ:**  
Выполняется стандартная последовательность команд:
```bash
git checkout main
git fetch upstream
git merge upstream/main
git push origin main
```
После этого локальная ветка `main` и удалённый форк `origin/main` содержат все последние коммиты родительского проекта.

### 8. Что такое защищённые ветки (Protected Branches) и зачем они нужны?
**Ответ:**  
Защищённые ветки — механизм политик безопасности в GitLab/GitHub, ограничивающий действия пользователей над критически важными ветками (`main`, `master`, `release/*`, `develop`).  
**Возможности:**
- Запрет прямого push коммитов всеми разработчиками (изменения допустимы только через Merge Request).
- Запрет операции `git push --force` (невозможность случайного удаления или переписывания истории).
- Требование обязательного прохождения тестов CI/CD перед слиянием.
- Требование обязательного одобрения (approvals) от мейнтейнеров или Code Owners.

### 9. В чём разница между методами слияния: "Merge commit", "Squash commits", "Rebase and merge"?
**Ответ:**  
- **Merge commit:** создаёт специальный коммит слияния с двумя родителями. Полностью сохраняет всю детальную хронологию коммитов feature-ветки.
- **Squash commits:** «схлопывает» все коммиты feature-ветки в один единственный аккуратный коммит, который добавляется в целевую ветку. Это очищает историю от промежуточных коммитов («исправил опечатку», «wip»).
- **Rebase and merge:** коммиты ветки поочередно переносятся поверх вершины целевой ветки без создания merge-коммита. Формируется строго линейная история, но меняются SHA-1 хэши коммитов.

### 10. Как добавить нескольких участников в GitLab-проект?
**Ответ:**  
В интерфейсе GitLab:
1. Открыть проект $\rightarrow$ в боковом меню перейти в раздел **Manage** $\rightarrow$ **Members**.
2. Нажать кнопку **Invite members**.
3. Ввести username, email или группу пользователей.
4. Назначить роль (уровень прав доступа):
   - `Guest` — только просмотр и создание issues.
   - `Reporter` — просмотр кода и веток.
   - `Developer` — создание веток, создание MR, push в незащищённые ветки.
   - `Maintainer` — слияние в защищённые ветки, управление настройками проекта и CI/CD.
   - `Owner` — полный контроль над проектом, включая удаление.
5. Установить срок действия прав (Expiration date при необходимости) и нажать **Invite**.
