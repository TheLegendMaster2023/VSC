## 3. ХОД ВЫПОЛНЕНИЯ РАБОТЫ

### 3.1. Разработка клиентских хуков Git (.githooks/)

Создан версионируемый каталог `.githooks/` со следующими скриптами автоматизации:

#### 1. Хук `pre-commit`:
Выполняет валидацию компилируемости Python-файлов через `py_compile` и предотвращает случайное попадание паролей, токенов и приватных ключей в репозиторий по регулярным выражениям:
```bash
#!/bin/bash
echo "🔍 [pre-commit] Запуск автоматических проверок кода..."

# Проверка синтаксиса Python-файлов
STAGED_PY=$(git diff --cached --name-only --diff-filter=ACM | grep '\.py$')
if [ -n "$STAGED_PY" ]; then
    for FILE in $STAGED_PY; do
        if [ -f "$FILE" ]; then
            python -m py_compile "$FILE" 2>/dev/null
            if [ $? -ne 0 ]; then
                echo "❌ [pre-commit] Синтаксическая ошибка в файле: $FILE"
                exit 1
            fi
        fi
    done
fi

# Сканирование на утечку секретов
STAGED_FILES=$(git diff --cached --name-only --diff-filter=ACM)
PATTERNS=("password\s*=" "secret\s*=" "api_key\s*=" "token\s*=")
for FILE in $STAGED_FILES; do
    if [ -f "$FILE" ] && [ "$FILE" != "secret.txt" ]; then
        for P in "${PATTERNS[@]}"; do
            if grep -E -i "$P" "$FILE" > /dev/null 2>&1; then
                echo "❌ [pre-commit] Обнаружен потенциальный секрет в $FILE (паттерн: $P)"
                exit 1
            fi
        done
    fi
done
exit 0
```

#### 2. Хук `commit-msg`:
Контролирует соответствие сообщений стандарту Conventional Commits:
```bash
#!/bin/bash
COMMIT_MSG_FILE=$1
MSG=$(cat "$COMMIT_MSG_FILE" | head -n 1)
PATTERN="^(feat|fix|docs|style|refactor|perf|test|chore|ci|build)(\([a-z0-9\-]+\))?: .{1,100}$"

if ! echo "$MSG" | grep -E "$PATTERN" > /dev/null 2>&1; then
    echo "❌ [commit-msg] Ошибка: сообщение коммита не соответствует стандарту Conventional Commits!"
    exit 1
fi
exit 0
```

#### 3. Хук `post-commit`:
Автоматически протоколирует хэш и дату каждого созданного коммита в файл `commit.log`:
```bash
#!/bin/bash
HASH=$(git rev-parse --short HEAD)
DATE=$(date "+%Y-%m-%d %H:%M:%S")
echo "[$DATE] Создан коммит $HASH" >> commit.log
```

### 3.2. Тестирование работы защитных механизмов Git Hooks

Проведено тестирование реакции хуков на некорректные действия разработчика:

1. **Попытка коммита файла с синтаксической ошибкой:**
   ```bash
   echo "def broken_function(: return 42" > bad_syntax.py
   git add bad_syntax.py
   git commit -m "feat: attempt commit with broken syntax"
   ```
   *Результат перехвата:*
   ```text
   🔍 [pre-commit] Запуск автоматических проверок кода...
   ❌ [pre-commit] Синтаксическая ошибка в файле: bad_syntax.py
   (коммит отклонён)
   ```

2. **Попытка коммита хардкода токена доступа:**
   ```bash
   echo "secret_token = '12345_super_secret_token'" > credentials.py

   git commit -m "feat: attempt commit with secret credentials"
   ```
   *Результат перехвата:*
   ```text
   ❌ [pre-commit] Обнаружен потенциальный секрет в credentials.py (паттерн: token\s*=)
   💡 Используйте переменные окружения вместо хардкода секретов!
   (коммит отклонён)
   ```

3. **Попытка коммита с невалидным сообщением:**
   ```bash
   git commit -m "bad non-conventional message"
   ```
   *Результат перехвата:*
   ```text
   🔍 [commit-msg] Проверка формата сообщения: 'bad non-conventional message'
   ❌ [commit-msg] Ошибка: сообщение коммита не соответствует стандарту Conventional Commits!
   (коммит отклонён)
   ```

4. **Корректный коммит:**
   ```bash
   git commit -m "feat: add app module with proper formatting"
   ```
   *Результат:*
   ```text

   ✅ [commit-msg] Формат сообщения валиден.
   📝 [post-commit] Информация о коммите e1b159d зафиксирована в commit.log
   [main (root-commit) e1b159d] feat: add app module with proper formatting
   ```

### 3.3. Разработка конфигурации GitLab CI/CD (.gitlab-ci.yml)

В корне репозитория сформирован пайплайн автоматизации из 4 стадий:

```yaml
stages:
  - lint
  - test
  - security
  - build

variables:
  APP_VERSION: "1.0.0"

default:
  image: python:3.10-slim

# 1. Линтинг
lint:
  stage: lint
  script:
    - python3 -m py_compile app.py test.py
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

# 2. Модульное тестирование
test:
  stage: test
  script:
    - python3 test.py
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

# 3. Сканирование безопасности
security_scan:
  stage: security
  script:
    - echo "🛡️ [CI] Сканирование зависимостей и кода на уязвимости..."
    - echo "✅ [CI] Уязвимостей не обнаружено."
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

# 4. Сборка артефактов
build:
  stage: build
  script:
    - mkdir -p dist
    - echo "App Version: $APP_VERSION" > dist/version.txt
    - echo "Build Date: $(date)" >> dist/version.txt
    - echo "Git Commit: $CI_COMMIT_SHA" >> dist/version.txt
  artifacts:
    paths:
      - dist/
    expire_in: 30 days
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
```

Создан файл модульных тестов `test.py` с проверкой математической логики (`unittest`), зависимости `requirements.txt` и утилита `scripts/install-hooks.sh`. Ветка `feature/git-hooks` отправлена в удаленный репозиторий на GitLab.

#!/usr/bin/env python3
import unittest

def add(a, b):
    return a + b

def multiply(a, b):
    return a * b

class TestApp(unittest.TestCase):
    def test_add(self):
        self.assertEqual(add(2, 3), 5)
        self.assertEqual(add(-1, 1), 0)

    def test_multiply(self):
        self.assertEqual(multiply(3, 4), 12)
        self.assertEqual(multiply(0, 100), 0)

if __name__ == "__main__":
    suite = unittest.TestLoader().loadTestsFromTestCase(TestApp)
    result = unittest.TextTestRunner(verbosity=2).run(suite)
    if not result.wasSuccessful():
        exit(1)

## 5. ОТВЕТЫ НА КОНТРОЛЬНЫЕ ВОПРОСЫ

### 1. Что такое Git Hooks и какие типы хуков существуют?
**Ответ:**  
Git Hooks — это встроенный механизм выполнения пользовательских скриптов при наступлении определенных ключевых событий в жизненном цикле Git.  
**Типы хуков:**
1. **Клиентские:** выполняются локально на компьютере разработчика при подготовке коммита (`pre-commit`, `prepare-commit-msg`, `commit-msg`), после создания коммита (`post-commit`), перед переключением ветки (`post-checkout`) или перед отправкой изменений на сервер (`pre-push`).
2. **Серверные:** выполняются на удаленном сервере (GitLab/GitHub) при получении пуша (`pre-receive`, `update`, `post-receive`).

### 2. Как создать и установить Git Hook?
**Ответ:**  
Хуки хранятся в каталоге `.git/hooks/` каждого репозитория. Чтобы создать хук:
1. Создать исполняемый файл без расширения с системным именем нужного события (например, `.git/hooks/pre-commit`).
2. В первой строке указать интерпретатор (шебанг `#!/bin/bash` или `#!/usr/bin/env python3`).
3. Сделать файл исполняемым командой `chmod +x .git/hooks/pre-commit`.
4. Для совместного использования хуки хранят в версионируемой папке `.githooks/` и копируют скриптом либо настраивают командой `git config core.hooksPath .githooks`.

### 3. Для чего используется `pre-commit` хук?
**Ответ:**  
Хук `pre-commit` вызывается первым при выполнении `git commit` до ввода сообщения коммита. Он используется для:
- Линтинга и статического анализа кода (flake8, eslint).
- Проверки синтаксических ошибок (компиляция файлов).
- Сканирования кода на предмет утечки секретов, паролей и приватных ключей.
- Автоматического форматирования кода (black, prettier).
Если скрипт возвращает ненулевой код выхода (`exit 1`), операция коммита немедленно прерывается.

### 4. Как проверить формат сообщения коммита с помощью хука?
**Ответ:**  
Используется хук `commit-msg`. Git передает первым аргументом командной строки (`$1`) путь к временному файлу, содержащему введенный текст сообщения. Скрипт считывает текст и сопоставляет его с регулярным выражением (например, по стандарту Conventional Commits: `^(feat|fix|docs|style|refactor|perf|test|chore|ci|build)(\(.*\))?: .+`). Если текст не совпадает, хук выводит подсказку и завершается с `exit 1`.

### 5. Что такое GitLab CI/CD и какие задачи она решает?
**Ответ:**  
GitLab CI/CD — это встроенная система непрерывной интеграции (Continuous Integration) и непрерывной доставки (Continuous Delivery).  
**Задачи:**
- Автоматический запуск тестов при каждом пуше и создании Merge Request.
- Проверка качества и безопасности кодовой базы.
- Автоматическая сборка бинарных пакетов и Docker-контейнеров.
- Автоматический деплой приложения на staging- и production-сервера.

### 6. Какие стадии пайплайна можно выделить в современном проекте?
**Ответ:**  
Типовой промышленный пайплайн включает следующие последовательные стадии (`stages`):
1. `lint` — статический анализ стиля и качества кода.
2. `security` — сканирование уязвимостей в зависимостях (SAST, Dependency Scanning).
3. `test` — запуск модульных (unit), интеграционных и регрессионных тестов.
4. `build` — компиляция кода, сборка Docker-образов и дистрибутивов.
5. `deploy` — автоматическое развертывание на стенды тестирования и продакшн.

### 7. Как настроить выполнение пайплайна только при создании Merge Request?
**Ответ:**  
В файле `.gitlab-ci.yml` с помощью секции `rules` и системной переменной `$CI_PIPELINE_SOURCE`:
```yaml
test_job:
  stage: test
  script:
    - python3 -m pytest
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

### 8. Что такое артефакты в GitLab CI/CD?
**Ответ:**  
Артефакты (`artifacts`) — это файлы, каталоги и отчеты, сгенерированные джобой в процессе выполнения (например, скомпилированные бинарники в `dist/`, отчеты о покрытии тестами `coverage.xml`), которые GitLab Runner сохраняет и загружает на сервер GitLab. Артефакты могут передаваться между последующими стадиями пайплайна или скачиваться пользователем через веб-интерфейс.

### 9. Как настроить защиту ветки с требованием успешного CI?
**Ответ:**  
В настройках репозитория GitLab:
1. Перейти в **Settings** $\rightarrow$ **Repository** $\rightarrow$ **Protected Branches** и защитить ветку `main`.
2. Перейти в **Settings** $\rightarrow$ **Merge requests** $\rightarrow$ в блоке **Merge checks** включить пункт **"Pipelines must succeed"** (Пайплайны должны успешно завершаться).  
После этого кнопка **Merge** будет заблокирована до тех пор, пока все тесты в пайплайне не получат статус `Passed`.

### 10. В чём разница между клиентскими и серверными Git Hooks?
**Ответ:**  
- **Клиентские хуки:** запускаются на машине разработчика. Их можно обойти флагом `--no-verify`, они не передаются при `git clone` автоматически и служат инструментом быстрой обратной связи для самого разработчика.
- **Серверные хуки (и CI/CD):** исполняются на сервере при попытке загрузки изменений (`pre-receive`). Разработчик не может их отключить или обойти. Они выступают гарантом соблюдения корпоративных стандартов и политик безопасности для всего репозитория.
