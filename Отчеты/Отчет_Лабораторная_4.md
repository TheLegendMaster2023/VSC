## 3. ХОД ВЫПОЛНЕНИЯ РАБОТЫ

### 3.1. Практика команд отмены изменений (reset, revert, restore, amend)

В ветке `feature/experiment` была создана серия коммитов, на которых последовательно протестированы режимы отмены:

#### 1. Soft reset (`git reset --soft HEAD~1`)
Коммит отменяется, однако сделанные в нем изменения файлов остаются в индексе (staging area):
```bash
git reset --soft HEAD~1
git status
```
*Консольный вывод:*
```text
On branch feature/experiment
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	new file:   file3.txt
```

#### 2. Mixed reset (`git reset --mixed HEAD~1`)
Коммит отменяется, файлы удаляются из индекса, но остаются в рабочей директории в виде модификаций:
```bash
git reset --mixed HEAD~1
git status
```
*Консольный вывод:*
```text
On branch feature/experiment
Untracked files:
	file3.txt
```

#### 3. Hard reset и спасение через Reflog (`git reset --hard` и `git reflog`)
Выполнен сброс последнего коммита с полным удалением изменений из рабочей директории:
```bash
git reset --hard HEAD~1
git reflog -n 3
```
*Консольный вывод:*
```text
HEAD is now at e92fefa feat: add file3
e92fefa HEAD@{0}: reset: moving to HEAD~1
b1c6a8a HEAD@{1}: commit: feat: add file4
```
С помощью журнала перемещения указателя `HEAD` (`git reflog`) видно, что удаленный коммит `b1c6a8a` доступен для восстановления в любой момент командой `git checkout b1c6a8a` или `git branch recovery b1c6a8a`.

#### 4. Безопасная отмена коммита (`git revert`)
В отличие от reset, команда revert создает новый противоположный коммит, не удаляя историю:
```bash
git revert HEAD --no-edit
git log --oneline -2
```
*Консольный вывод:*
```text
75f159b Revert "fix: corrupt data"
a314a89 fix: corrupt data
```

#### 5. Исправление коммита на месте (`git commit --amend`)
Исправлена опечатка в сообщении последнего коммита без создания дублирующих записей:
```bash
git commit --amend -m "feat: add app function"
```

### 3.2. Интерактивный rebase (`git rebase -i`)

Создана цепочка из 5 коммитов (`feat: add line 1` ... `feat: add line 5`).

С помощью команды:
```bash
git rebase -i HEAD~5
```
выполнена операция **`squash`** (объединение коммитов строк 1, 2 и 3 в один результирующий коммит):

```text
pick 4911544 feat: add line 1
squash 10097cf feat: add line 2
squash a6c9656 feat: add line 3
pick 3c50e6d feat: add line 4
pick 45e8da4 feat: add line 5
```

*Консольный вывод лога после сжатия:*
```text
509545e feat: add line 5
af1dfed feat: add line 4
d9a955c feat: add lines 1 to 3 combined with squash
```

### 3.3. Принудительный push и безопасный ключ `--force-with-lease`

Ветка `feature/rebase_experiment` была отправлена в GitLab. После этого локально был переписан последний коммит через `commit --amend`.

1. **Обычный push отклонен сервером:**
   ```bash
   git push origin feature/rebase_experiment
   ```
   *Вывод:*
   ```text
   ! [rejected] feature/rebase_experiment -> feature/rebase_experiment (non-fast-forward)
   error: failed to push some refs
   hint: Updates were rejected because the tip of your current branch is behind
   ```

2. **Безопасная принудительная отправка:**
   ```bash
   git push --force-with-lease origin feature/rebase_experiment
   ```
   *Вывод:*
   ```text
   + 509545e...eec851a feature/rebase_experiment -> feature/rebase_experiment (forced update)
   ```
   Флаг `--force-with-lease` защищает от перезаписи чужой работы: если бы кто-то из коллег успел отправить свой коммит, push был бы отклонён.

## 5. ОТВЕТЫ НА КОНТРОЛЬНЫЕ ВОПРОСЫ

### 1. В чём разница между `git reset` и `git revert`? Когда что использовать?
**Ответ:**  
- `git reset` перемещает указатель текущей ветки назад во времени, физически вычеркивая последующие коммиты из цепочки. Применяется **только на локальных ветках**, которые еще не были опубликованы на общем сервере.
- `git revert` не удаляет старые коммиты, а создает абсолютно **новый коммит**, который вносит прямо противоположные изменения (откатывает правки). Применяется для **публичных и общих веток** (`main`, `develop`), так как не нарушает историю коллег.

### 2. Что делает `git reset --hard` и почему это опасно?
**Ответ:**  
`git reset --hard <commit>` перемещает указатель ветки, очищает индекс (staging area) и **безвозвратно стирает все изменения в рабочей директории**, приводя файлы к точному состоянию указанного коммита. Это опасно, поскольку все незакоммиченные правки теряются навсегда без возможности восстановления через Git.

### 3. Какие действия можно выполнить с помощью интерактивного rebase?
**Ответ:**  
Команда `git rebase -i` позволяет:
- `pick` — оставить коммит без изменений.
- `reword` — изменить текст сообщения коммита.
- `edit` — прервать процесс для внесения правок в файлы коммита.
- `squash` — склеить коммит с предыдущим, объединив их сообщения.
- `fixup` — склеить коммит с предыдущим, отбросив сообщение текущего.
- `drop` — удалить коммит из цепочки.
- Изменить порядок коммитов (путем перестановки строк в файле todo).

### 4. Как объединить несколько коммитов в один с сохранением их сообщений?
**Ответ:**  
С помощью команды `git rebase -i HEAD~N`. В открывшемся списке напротив первого коммита оставляется команда `pick`, а напротив всех последующих, которые нужно влить в него, указывается ключевое слово `squash` (или `s`). При сохранении Git откроет редактор со сводным текстом всех объединяемых сообщений для редактирования.

### 5. Как изменить сообщение последнего коммита без создания нового?
**Ответ:**  
С помощью команды:
```bash
git commit --amend -m "Новое правильное сообщение"
```
Она перезаписывает самый верхний коммит текущей ветки.

### 6. Почему `git push --force` считается опасной операцией?
**Ответ:**  
Ключ `--force` принудительно перезаписывает ветку на удаленном сервере состоянием вашей локальной ветки. Если за время вашей работы кто-то из коллег успел отправить свои коммиты в эту ветку, они будут **безвозвратно затерты** на сервере без каких-либо предупреждений.

### 7. Что такое `--force-with-lease` и чем он лучше обычного `--force`?
**Ответ:**  
`--force-with-lease` — это безопасный вариант принудительного push. Git проверяет, совпадает ли текущее состояние ветки на сервере с той ревизией, которую вы скачали последней (`remote-tracking ref`). Если удаленная ветка изменилась (коллега запушил новый коммит), Git откажется выполнять перезапись и предотвратит потерю чужой работы.

### 8. Как восстановить коммит, удалённый через `git reset --hard`?
**Ответ:**  
1. Выполнить команду `git reflog`, чтобы увидеть историю всех перемещений указателя `HEAD`.
2. Найти хэш потерянного коммита (например, `b1c6a8a`).
3. Создать новую ветку от этого хэша:
   ```bash
   git branch recovery-branch b1c6a8a
   ```
   Либо переместить текущую ветку обратно: `git reset --hard b1c6a8a`.

### 9. В каких случаях используется `git revert`, а в каких — `git reset`?
**Ответ:**  
- `git reset` используется, когда вы экспериментируете **локально**, еще не отправили коммиты в удаленный репозиторий и хотите очистить черновики или перегруппировать коммиты.
- `git revert` используется, когда ошибочный коммит уже находится на **общем сервере** в ветках команды (`main`, `release`), чтобы отменить ошибку прозрачно для всех участников.

### 10. Почему не рекомендуется использовать `rebase` на общих ветках?
**Ответ:**  
«Золотое правило rebase»: никогда не применять rebase к публичным веткам. Перебазирование уничтожает существующие коммиты и создает новые с иными SHA-1 хэшами. Если эти коммиты уже скачаны другими разработчиками, при попытке синхронизации у них возникнет раздвоение истории, дублирование коммитов и массовые конфликты слияния.
