## 4. ОТВЕТЫ НА КОНТРОЛЬНЫЕ ВОПРОСЫ

### 1. Что такое распределённая система контроля версий и чем она отличается от централизованной?
**Ответ:**  
Централизованная VCS (например, SVN, CVS) хранит историю изменений на едином центральном сервере; если сервер недоступен, разработчики не могут фиксировать коммиты или просматривать историю.  
Распределённая VCS (Git, Mercurial) предоставляет каждому разработчику **полную локальную копию всего репозитория** со всей историей веток и коммитов. Это позволяет работать автономно (офлайн), быстро выполнять операции (все операции локальны) и обеспечивает надежность (каждый клон является резервной копией).

### 2. Для чего нужен SSH-ключ при работе с GitLab?
**Ответ:**  
SSH-ключ обеспечивает асимметричное криптографическое шифрование и аутентификацию пользователя. Вместо передачи и хранения пароля открытым текстом или необходимости постоянного ввода логина и пароля при каждой операции `push`/`pull`, сервер GitLab проверяет открытый ключ (`id_ed25519.pub`), соответствующий закрытому ключу на локальном компьютере (`id_ed25519`), что гарантирует безопасность соединения и удобство разработки.

### 3. В чём разница между `git add` и `git commit`?
**Ответ:**  
- `git add` переносит изменения из рабочей директории (Working Directory) в область подготовки / индекс (Staging Area), подготавливая конкретные файлы или фрагменты к фиксации.
- `git commit` берёт текущее состояние индекса и создаёт неизменяемый снимок (snapshot) состояния проекта в базе объектов Git с метаданными (автор, время, сообщение, хэш, ссылка на родителя).

### 4. Что такое staging area (индекс) в Git?
**Ответ:**  
Staging area (индекс) — это промежуточный буфер между рабочей директорией разработчика и постоянной историей коммитов. Индекс позволяет формировать атомарные, логически завершенные коммиты, добавляя только те изменённые файлы (или даже отдельные строки), которые относятся к текущей решаемой задаче.

### 5. Как проверить, какие файлы были изменены, но ещё не добавлены в коммит?
**Ответ:**  
- Команда `git status` отображает список отслеживаемых, но модифицированных файлов (*Changes not staged for commit*), а также неотслеживаемых (*Untracked files*).
- Команда `git diff` показывает точные построчные изменения в рабочей директории, которые ещё не были проиндексированы командой `git add`.

### 6. Для чего нужен файл `.gitignore`? Приведите примеры.
**Ответ:**  
Файл `.gitignore` указывает Git, какие файлы и директории следует игнорировать и не отслеживать в репозитории. Это предотвращает случайное попадание в репозиторий:
- Артефактов сборки и бинарных файлов (`*.exe`, `*.dll`, `dist/`, `build/`).
- Зависимостей сторонних пакетов (`node_modules/`, `venv/`).
- Системных мусорных файлов (`.DS_Store`, `Thumbs.db`).
- Локальных настроек редакторов (`.idea/`, `.vscode/`).
- Секретов и токенов (`.env`, `*.pem`).

### 7. Как связать локальный репозиторий с удалённым?
**Ответ:**  
С помощью команды добавления удалённого репозитория:
```bash
git remote add origin <URL_репозитория>
```
Где `origin` — стандартный псевдоним удалённого сервера, а `<URL_репозитория>` — адрес по протоколу SSH (`git@gitlab.com:username/repo.git`) или HTTPS (`https://gitlab.com/username/repo.git`).

### 8. Чем отличается `git fetch` от `git pull`?
**Ответ:**  
- `git fetch` скачивает все новые коммиты, ветки и теги из удалённого репозитория в локальную базу данных, но **не объединяет** их с текущей рабочей веткой. Состояние рабочей директории остаётся неизменным.
- `git pull` выполняет два действия сразу: сначала делает `git fetch`, а затем автоматически вызывает `git merge` для слияния удалённой ветки с текущей локальной веткой.
